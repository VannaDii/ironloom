# Shared factory contract candidate

Status: contract candidate for Ivy compatibility review, based on planning revision `3da9d8573d5c38bf3d55414b08cdc7808b5144d0`. This implements validated types, schemas, deterministic decode fixtures, fresh-install schema constraints and adapter interfaces. It does not implement a running factory, authentication provider, native relay, model engine, scheduler or Flutter application. Temporary foundation code is retired as replacements land; it provides no old-version compatibility contract. No inference, device discovery, Mac checks or backend qualification is performed here.

## File ownership and toolchain

Ironloom is unreleased. Use fresh-schema initialization only. Do not add backward compatibility shims, legacy wire/artifact formats or runtime adapters, data conversion/backfills, schema upgrades, migration history, or migration frameworks. Obsolete foundation code may remain only until its replacement lands during initial build-out; it must not become supported old-version behavior.

Use Rust **1.96.0**, pinned in `rust-toolchain.toml` and available on both remote hosts. The initial exploratory build used 1.99.1; the candidate is checked using the common pin. Adapters report capabilities/observations and perform authorized operations; they do not choose fallback engines/models/billing or execute generated tools. No MLX/Splash dependency or engine version is selected by these interfaces.

## Decode and validation

New factory wire models are aliases of `Validated<ModelData>`. `ModelData` is an unchecked construction draft; only the immutable validated alias may enter domain logic or application state. `Validated::new`, normal serde deserialization and `ironloom_core::validation::decode::<Model>` use the same `Validate` implementation. Nested aliases validate recursively. Cross-field errors contain `fields: [{field, code}]` with dot-separated paths and numeric array segments such as `messages.1.text`; parsing failures use `invalid_structure` without echoing submitted data. Authentication input Debug output is redacted. Authentication and live resource authorization still run after validation.

Counters, timestamps, byte/token totals, event sequences and revisions are **canonical decimal strings**, including zero, bounded by unsigned 64-bit range. JSON numbers, leading zeros, signs, overflow and trailing input are rejected. Dart must parse without a JavaScript floating-point conversion. `fixtures/contracts/decode.json` is the shared valid/invalid decode-path corpus; Rust exercises it in `factory_decode.rs`, and Ivy must exercise the same corpus in Dart. JSON Schema describes structure; semantic validation remains required for nested/cross-field invariants and the exact counter maximum. Typed string identities invoke their constructors during deserialization. There are no old-format decoders or converters.

The cookie/token transport, session persistence and password/OIDC implementations are backend build-out work, not claimed by the port definitions. State-changing cookie-authenticated operations require CSRF/origin enforcement. Never accept worker-supplied identity as authenticated identity. `PlanApproval.approved_by` must match the authenticated approver, and the backend checks the stored plan ID/revision/content hash and current permission; the DTO itself is not approval authority.

SSE event name is `ironloom.event`; data is serialized `ServiceEvent`. Its ID is URL-safe, unpadded base64 of the scoped `ReplayCursor` JSON. Decode through `decode_cursor`, then authorize its conversation. An expired cursor yields `CursorExpired`, requiring explicit snapshot/resync; an unavailable store yields `Unavailable`. Cursors are replay positions, never grants. PostgreSQL stores full-range counter sequences as `numeric(20,0)` rather than a signed bigint or floating point.

`FactoryStore::commit_command` defines the actor/key/hash, receipt, initial event and dispatch outbox transaction. Duplicate keys return existing outcome or conflict, with no new dispatch. Outbox consumers still need renewable claims/fences and reconciliation; a transaction/outbox does not promise exactly-once external mutations or inference. The fresh initializer establishes singleton bootstrap, authenticated identity, node/project/conversation, command/event and outbox constraints. Further initial-build domain tables are authored in the same fresh schema, without upgrade files, conversion or migration history. Connection/key failures never initialize a replacement installation or database.

Administrator access to a private project requires an explicit recorded self-grant before viewing. Project creator ownership and view/operate/approve/manage presets remain distinct. Credential use/replacement/sharing/deletion are separate grants. The tool gateway checks the authenticated operator and worker delegation, current grants using higher consistency, exact resources and approved scope before native isolation. `Denied`, `Unavailable` and `ApprovalRequired` never dispatch. Enrollment requires administrator authority and a signed/authenticated node registration bound to the installation and physical host; `key_access_ref` references infrastructure-controlled protected key access for that enrolled node, never plaintext shared keys in client responses. The key-resolution backend is not implemented here. All nodes use the same current protocol; there is no old-version compatibility path.

## Execution, learning and resources

Plan approval binds a revision and content hash; steering binds an expected active turn; answers bind pending question/turn/item/revision and carry multiple `choices` plus optional nonblank `text`. Pending questions expose `allow_multiple` and `allow_text`, including text-only questions. `validate_response` checks the response against those modes and the stored choices, independently of revision/identity checks and atomic resolution. The backend must reject replaced/resolved/stale requests. Copied instructions track applied and acknowledged revisions; the explicit preserve/update choice is separate from immediate lesson notifications. Already-running inference cannot acknowledge a later instruction revision.

Lesson setup has no default: missing handling mode or delivery confirmation prevents execution readiness. Each lesson records its origin/source, scope and revision independently of cleanup. Every mode applies locally immediately, subject to explicit per-lesson restrictions. Share/manage/view grants are distinct; sharing content grants no access to its private source. Revision/change/restriction/deletion invalidates retrieved worker context at the next decision boundary. Remembered answers retain wording, human identity, timestamp, scope and supersession; similarity or a lesson never substitutes for approval.

`ExecutionState` is shared by scheduler/adapters. Waiting for a human/resource and pause are resumable. Cancellation requested is distinct from terminated; stream EOF/disconnect is never completion. Workers emit start/delta/tool-ready/wait/usage/completion/failure/termination events with assignment/worker/turn/item IDs. Partial tool arguments cannot execute; complete calls still enter the gateway. Output consumption and monitoring remain independent of viewer speed. Budget edits change subsequent dispatch, include in-flight reservations and uncertain usage, and do not revise plan approval or disable generation limits. Account usage is not API-key billing.

One assignment has one shared worktree on its owning node. Relative path drafts reject obvious traversal, while actual filesystem/symlink and descendant enforcement remains native execution work. Validation binds exact content plus a mutation fence after active edits drain. Relevant edits invalidate results; cleanup waits for worker release and preservation of needed changes.

Physical host and node identity differ. Reconciled GPU identity/parent partitions share one capacity authority across container aliases; unresolved identity blocks admission. Reserve memory/concurrency before loads and include cache/draft/overhead demand. Lease loss stops admissions; expiry alone never proves old execution stopped. Local selections include engine/version/backend/configuration, checkpoint/revision/quantization and placement. Active inference protects residency; an idle worker or tool wait does not. Cancellation is request-scoped, not resident-model-wide. Compatibility, estimated fit and actual hardware qualification remain separate.

`FactoryArtifact` records have project/assignment/correlation identity and no Discord thread binding. Obsolete foundation artifact/runtime/index code is retired as replacements land; it is not retained as a compatibility reader, alternate supported format or conversion target.

## Compatibility additions from Ivy review

`FactoryService::snapshot` returns one consistent `ConversationSnapshot` with the same authorized conversation and durable watermark across its state. Approval must match the visible plan ID/revision/hash. `history` reads `HistoryQuery.as_of` and returns role-bearing `HistoryItem` records with a stable `next_before` cursor pointing at the oldest item in that page. History is oldest-to-newest within a page; the next page is older. New events do not change that snapshot-bound view. Retention loss yields `CursorExpired` rather than an invented partial history.

`FactoryService::subscribe` must atomically bridge replay after a supplied durable cursor into live delivery, with no missing event between the two phases. `EventSubscription.events` is a bounded Tokio receiver of `Result<ServiceEvent, ServiceError>`; overflow yields `ResyncRequired` and closes the feed when possible. Abrupt closure is also a reconnect condition. Reauthorize live delivery and close on revocation. The viewer reconnects from its last consumed durable cursor without resubmitting work. These are port guarantees for the backend implementation, not a claim that a subscription service has been implemented or tested end-to-end.

`InferenceRequest` now includes target turn/item IDs and typed ordered `InferenceMessage` values. Roles are system/developer/user/assistant/tool. Assistant messages may carry text and/or complete `ToolInvocation` records; tool messages carry one matched `ToolResult` and a succeeded/failed outcome. Requests include current `ToolDefinition` schemas instead of names alone. Validate object argument/schema structure, unique tool names/call IDs and ordered complete call/result pairs before provider mapping. Full JSON Schema compilation and authorization of proposed calls still belong to the gateway; historical tool content never grants permission for a new call. Providers map these values into their own HTTP payloads and never execute tools. Partial streamed tool arguments remain fragments until complete and independently validated.

`RelayTarget` carries distinct WebSocket, enrollment, refresh, pairing and pairing-status endpoints on one normalized origin; secure transport is required except loopback fixtures, matching the pinned source. The protected node/client setup still chooses an allowed target; validation does not authorize arbitrary relay endpoints. `NativePersistenceKey` is the upstream lookup tuple of WebSocket target, external account and optional client name. Enrollment validates that its target/account match that key, and keeps server ID, environment ID and authentication generation distinct. The pinned [persistence source](https://github.com/openai/codex/blob/e2e7dabd4587c7b0fbf934e6a93b6cec8245751d/codex-rs/app-server-transport/src/transport/remote_control/persistence.rs) was inspected for these keys; its SQLite implementation is not adopted.

Native and runtime depend on `ironloom-service`; the native crate must not depend on runtime. Imports use the new owning crate directly, with no old-path re-exports. ### Model browser assessments

`POST /api/v1/models/assessments` accepts `ModelAssessmentQuery` and returns `Vec<EngineAssessment>` through `FactoryService::assess_model`. The query selects the exact source repository/revision, optional authorized project/profile, optional explicit engine/version/backend and explicit context/concurrency assumptions. Each result is one engine and canonical device placement/group, with existing `EngineRequirements` and `ModelFit` data. The service combines current configured engine capabilities and optional static driver requirements with reconciled shared resource authority; it does not sum duplicate aliases/overlapping partitions or assume unsupported multi-GPU pooling. Full memory demand includes weights, draft, KV/cache, runtime/concurrency overhead and accelerator requirements; fit accounts for headroom, external pressure, outstanding reservations and eligible idle eviction. Missing metadata, identity, observations or demand components remain unknown. Unsupported capabilities remain explicit. Qualification is independently sourced per backend/hardware placement and defaults to unqualified in this phase. No generation, warm-up or model loading is used to obtain an assessment. An absent profile does not silently select a role model or engine for execution; it browses configured candidates only.

### Authorized installed-model inventory

`GET /api/v1/models/inventory` accepts `ModelInventoryQuery` and returns `ModelInventoryPage` through `FactoryService::inventory`. `ModelInventoryItem` carries a stable inventory ID, existing `ModelCard` provenance, optional download ID, explicit `transfer_complete`, independent `ModelVerification`, successful checkpoint-manifest hash/time, and current `storage_available`. Matching transferred/total byte counts never sets installation verification. Pending/failed records have no successful verification hash/time; verified records require confirmed transfer completion and a checked manifest. Missing model storage preserves metadata/provenance but blocks use. Source/account/license authorization, integrity, engine compatibility, memory fit and actual backend qualification remain separate. The browser has no operation to assert verification; only the trusted installation pipeline persists its result after verifying required files/checksums. File hashes/manifests are retained once, not recomputed for each inference. Pagination and publisher/host/verification filters apply only to currently authorized inventory entries.

### Installation and empty-conversation command persistence

`StoredCommand` allows absent project/conversation scopes for installation configuration before projects exist. Conversation scope requires project scope. Its optional first event permits an empty conversation to commit its metadata, validated snapshot and actor-scoped receipt with cursor zero and no event/outbox dispatch. The concrete PostgreSQL transaction API commits configuration revision checks with command identity, and conversation creation binds the command even without an event. Reusing an actor/key with a changed fingerprint conflicts; retries return the original receipt. `FactoryStore` is implemented by the PostgreSQL store, including event-free commands and atomic lesson context invalidation.

`DownloadProgress.repository_id` retains the authorized repository binding needed for resume/cancel, separately from source provenance and verified installation state.
